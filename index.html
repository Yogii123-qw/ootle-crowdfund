SIMULATION — no wallet, no network, no real funds

Ootle Crowdfund

All-or-nothing crowdfunding. A creator sets a goal and an epoch deadline. Backers pledge TARI into a vault. Goal met by the deadline → the creator claims it all. Goal missed → every backer refunds in full. No platform cut, no custody beyond the template.

This page runs a faithful in-browser simulation of the CrowdfundCampaign Rust template — same rules, same rejection messages. The template itself is tested against the real Ootle engine (cargo test). Nothing here touches a network or a wallet.

Judge walkthrough (~2 minutes)

Follow the steps. Each one ticks itself off as you do it. Rejections are part of the demo — they prove the template says no exactly when it should.

  1. Pledge 400 as Bima on Community radio.
  2. Pledge 600 as Sari on Community radio — watch the goal fill and the Funded event fire.
  3. Try Claim as Rani before the deadline — it must be rejected.
  4. Advance the epoch to 5 (the deadline).
  5. Claim Community radio as Rani — the full vault pays out.
  6. Pledge on Neighborhood mural, then Refund after the deadline — full repayment.
  7. Refund the same pledge again — it must be rejected (double refund).
  8. Try refunding Community radio — it must be rejected (refunds closed after success).

Tip: switch the active persona with the “Acting as” control. The active persona is the transaction signer — the template checks it on every call.

    How it works

    • One campaign = one component. new(title, goal, deadline_epoch) opens it; the caller becomes the creator.
    • Escrow vault. pledge(bucket) deposits TARI into the campaign vault and records the backer in a ledger. Pledges accumulate; overfunding is allowed.
    • Epoch deadline. Pledges are accepted while current_epoch < deadline_epoch. At current_epoch >= deadline_epoch the campaign settles — the boundary is tested both ways.
    • Exactly one outcome. Goal met → claim() pays the whole vault to the creator, once. Goal missed → refund() repays each backer in full, once. The other path is rejected with a specific message.
    • Events. CampaignCreated, Pledged, Funded (once, when the goal is first reached), Claimed, Refunded — indexable by explorers.
    • Access rules. Methods are callable by anyone; authorization is enforced in code by comparing the transaction signer to the recorded creator/pledge keys. The template creates no resource, so there are no owner-bypassable resource rules.

    Honest limits — read before judging

    • This page is a simulation. No template has been published to Esmeralda or mainnet, and no on-chain state exists. The simulation mirrors the template rules and is parity-tested (node --test app/sim.test.mjs); the template rules are proven against the real engine (cargo test, 12 tests).
    • Pledge amounts are public. Vault-based accounting means anyone can read who pledged how much. That is a deliberate v1 design choice, not an oversight. Hiding amounts would need a confidential/stealth design and is out of scope.
    • No partial refunds, no milestones, no platform fee. All-or-nothing, one claim, full refunds. Stretch ideas are listed in the README, not claimed here.
    • Live mode is not wired up. The section below detects a Tari wallet but cannot transact: no template address is published, so there is nothing to call. It will honestly say so. Never trust a demo that claims a live path it cannot show.
    • Epochs are coarse on real networks (~20 min mainnet, ~1 h Esmeralda), so real campaigns run for days, not minutes. The demo's epoch control exists only to make the story judgeable in two minutes.

    What live mode would need: a published template address on Esmeralda/mainnet, the window.tari provider (Sapient extension or Tari Universe web wallet), and indexer reads for campaign discovery.
